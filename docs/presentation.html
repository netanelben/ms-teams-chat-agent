Teams requirements agent

A signed-in Teams session watches one colleague’s chat. GPT-4o asks for the missing pieces of a task. When the request is complete, a second chat receives a structured brief.

60sDefault poll of the newest chat bubble
gpt-4oOne system prompt, the whole thread resent each turn
3–7sRandom pause before a conversational reply

Two ways in, one monitor

Local Chrome and an Anchor cloud browser are launchers. Both hand a Playwright page to runTeamsMonitor. The decision loop does not know which browser it is driving.

The first local launch may wait on a manual sign-in. The profile directory is gitignored, so the session stays on the machine.

What happens to one message

Each wake-up reads a single bubble: the newest one in the requester’s chat. The model picks a contract. The monitor decides what actually gets typed.

A chat reply waits a random 3–7 seconds. The task brief is sent immediately, then conversation history is cleared.

The only three replies

The prompt is allowed to return one of these. processIncomingMessage is what the requester and the target actually see.

1

Follow-up

The model writes ordinary prose because a detail is missing. It is told to ask one or two questions.

The code lowercases it, strips lists and fences, restores names, pauses, and types into the source chat.

which env is this for?

2

Defer

The model wraps NEED_TO_CHECK when a direct answer would be a guess.

That completion is discarded. The same pause, then one fixed sentence. The thread stays open.

one moment, let me check that and get back to you

3

Task ready

The model wraps JSON in TASK_READY: title, description, priority, details, original request.

The monitor opens the target chat and sends this shape. No pause, no lowercase pass. History resets. The brief below is an example, not a captured chat.

New Task from the requester: Title: Restart payments worker Priority: high Description: Restart the worker in staging after 18:00. Details: Staging only. No production. Window is tonight. Original request: "please restart the payments worker"

How to walk it

Order that holds up

  1. The agent types as the signed-in user, in chats that account can already open.
  2. Point at the seam: both scripts end by calling runTeamsMonitor(page).
  3. Walk one new id into evaluateWithLLM, then the three branches.
  4. Close on the limit you would fix next: keep a queue of unread bubbles, and store the thread somewhere that survives a restart.

Name these first

  • Only the newest bubble is read. A burst keeps the last message.
  • Match is the display name in the chat list, not a user id.
  • Teams DOM test ids are the integration. A redesign breaks the poll.
  • Memory is a module-level array. It clears after a handoff, and it is empty after a restart.
